# Handoff: Alaska/Bering-Strait CrocoDash domain smoke tests → Derecho

## Goal
Compare three ways of building the same regional MOM6 domain around the Bering
Strait, to see which builds/runs cleanly through CrocoDash → CESM → MOM6
before committing to one. This is a **smoke test**, not a scientific
comparison — success = clean build + run, not model accuracy.

## The three domains
- **`alaska_latlon`** — plain lat/lon `Grid`, box 63–68N, 160–170W, 1/12°
  resolution. Cell area varies with latitude (~3.3e7–3.9e7 m²).
- **`alaska_albers`** — `Grid.from_projection(crs="EPSG:3338")` (Alaska
  Albers), same 63–68N, 160–170W box. Near-uniform cell area.
- **`alaska_albers_wide`** — also `Grid.from_projection(crs="EPSG:3338")`,
  wider/shorter box (~63.5–67N, 160–177.5W as last tuned in the notebook) to
  cover both the Seward Peninsula (Alaska side) and the Chukotka Peninsula
  (Russian side) of the strait, not just the eastern half.

All three use the same resolution: `resolution_m` for the two projected grids
was derived from `alaska_latlon`'s **actual mean T-cell area**
(`sqrt(mean(tarea))` ≈ 5967 m), not a naive `111_320 * (1/12)` degree→metre
conversion — that naive version ignores the `cos(lat)` shrinkage of zonal
spacing and overestimated cell area by ~2.4x at this latitude. This keeps all
three grids genuinely comparable at "1/12°-equivalent" resolution.

## Key constraint: YAML can't express `Grid.from_projection()`
`CrocoDash/recipe.py::build_grid` only supports a plain lat/lon `Grid(**cfg)`
or `Grid.from_supergrid(path)` — **not** `from_projection()`. So:
- `alaska_latlon.yaml` expresses its grid natively (`resolution`/`xstart`/
  `lenx`/`ystart`/`leny`) — no file dependency.
- `alaska_albers.yaml` and `alaska_albers_wide.yaml` use
  `grid.supergrid_path`, pointing at the `.nc` files generated by the
  notebook. **These two `.nc` files must be copied from the laptop to
  Derecho** (e.g. onto `/glade/...`), and `supergrid_path` in both YAMLs
  updated from the `<PATH_ON_DERECHO>` placeholder to the real path.

## Design choices baked into all three YAMLs (change if not wanted)
- **Compset**: `1850_DATM%NYF_SLND_SICE_MOM6%REGIONAL_SROF_SGLC_SWAV_SESP`
  (idealized NYF atmospheric forcing, no BGC/runoff) — chosen for a fast,
  minimal-data-footprint smoke test. NYF requires `atm_grid_name: T62` (not
  `TL319`, which is for JRA) — already set.
- **Ocean forcing**: `product_name: reference_ocean`,
  `function_name: get_reference_ocean_data` — CrocoDash's built-in synthetic,
  in-memory forcing generator (`CrocoDash/raw_data_access/datasets/reference.py`),
  explicitly documented as "for use in tests and demo notebooks," not a real
  reanalysis. Chosen so the smoke test doesn't depend on GLORYS/Copernicus/RDA
  access. **Open decision for whoever picks this up**: now that you're on
  Derecho (NCAR network), real GLORYS via `get_glorys_data_from_rda` becomes
  a realistic option if a more meaningful (not just build-clean) test is
  wanted later — swap `product_name`/`function_name` in the `forcings:` block
  if so.
- **Vertical grid**: `nk: 10`, uniform — deliberately small for build/run
  speed; raise once builds are confirmed clean.
- **Topo**: flat, `depth: 3000.0` — avoids needing a real bathymetry
  (GEBCO) file for the smoke test.
- **Forcing date range**: 5 days (`2020-01-01` to `2020-01-05`) — short, for
  speed.

## Known environment gap (laptop-side only)
None of the local conda envs (`CrocoDash`, `CrocoDashNew`, `CrocoDash.t.1`,
`CrocoDash.t.2`) have `ruamel.yaml` installed, so
`from CrocoDash.recipe import load_config` (the real structural validator)
fails on import (`regional_mom6` → `ruamel.yaml` missing) even though direct
`CrocoDash.grid.Grid` usage works fine — that's why the notebook ran but the
YAML configs were only checked against a hand-copied version of
`validate_config_structure`, not the real one. Worth confirming the Derecho/
container CrocoDash environment doesn't have the same gap before relying on
`crocodash create --config ...` there.
